## 지금 저장소 상태

- 변경 파일 목록: !`git status --short`
- 변경 규모: !`git diff --stat`

## 요청

$ARGUMENTS

## 너의 임무

위 변경 내용을 **코딩 초보인 사용자**가 이해할 수 있게 한국어로 설명한다.
이 사용자는 일본어 N5 학습용 단일 HTML 웹앱을 만들고 있으며,
HTML/CSS/JavaScript를 이제 막 접한 상태다.

### 1. 설명할 대상 정하기

- `$ARGUMENTS`에 파일명이 있으면 그 파일의 변경만 설명한다.
- 비어 있으면 **커밋되지 않은 변경 전체**를 설명한다.
- 커밋되지 않은 변경이 없으면 **가장 최근 커밋**(`git show HEAD`)을 설명한다.
- ⚠️ 새로 만든 파일은 `git diff`에 나오지 않는다.
  `git status`에 `??`로 표시된 파일은 **Read로 직접 읽어서** 설명에 포함한다.

### 2. 설명 형식

다음 순서를 지킨다.

**① 한 줄 요약**
"이번에 무엇이 달라졌는지"를 한 문장으로. 코드 용어 없이.

**② 바뀐 것들 (묶음별로)**
변경을 3~6개의 의미 단위로 묶고, 각각에 대해:

- **무엇을 바꿨나** — 한 문장
- **왜 바꿨나** — 이게 가장 중요하다. 어떤 문제를 풀려고 한 건지 설명한다.
- **어떻게 동작하나** — 흐름을 순서대로. 필요하면 3~5줄 이내의 짧은 코드 인용.
- 위치는 `index.html:123` 형식으로 적어 바로 찾아갈 수 있게 한다.

**③ 새로 나온 개념**
이번 변경에서 처음 등장한 문법이나 개념이 있으면 여기서 따로 설명한다.
반드시 **일상적인 비유**를 든다.

예시 톤:
> `setTimeout(함수, 700)` — "0.7초 뒤에 이 일을 해라"라고 예약해 두는 알람입니다.
> 정답을 맞혔을 때 잠깐 초록색을 보여준 뒤 다음 문제로 넘어가려고 썼어요.

**④ 직접 확인하는 법**
브라우저에서 무엇을 눌러보면 이 변경을 눈으로 확인할 수 있는지 1~3줄로.

### 3. 지켜야 할 것

- 영어 전문용어를 그대로 두지 않는다. 반드시 한국어로 풀어쓰고,
  원어가 필요하면 괄호로 병기한다. (예: 배열(array) = 값들을 순서대로 담은 목록)
- 바뀌지 않은 코드는 설명하지 않는다.
- 파일 전체를 붙여넣지 않는다. 인용은 꼭 필요한 몇 줄만.
- 변경이 위험하거나 나중에 문제가 될 소지가 있으면 마지막에 한 줄로 알린다.
- 전체 길이는 화면 1~2개 분량. 길어지면 ②의 묶음 수를 줄인다.
